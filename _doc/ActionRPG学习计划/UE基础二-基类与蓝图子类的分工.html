C++ 写好了类，引擎却跑的是蓝图
看懂 UE 这套「基类被蓝图化」的把戏

UE 基础 · 第二阶段　|　面向有 C++ 底子、零 UE 正向开发经验的读者　|　本页在原文基础上加了一组关系图，帮你把零散知识点串成一张网。

刚从纯 C++ 转过来做 UE 的人，几乎都会被同一件事绊倒：你在 Source/ 里翻到一个写得有模有样的 ARPGGameModeBase，满心以为引擎跑的就是它，结果运行起来根本不走你的断点。配置文件里引用的压根不是这个 C++ 类，而是一个叫 BP_GameMode_C 的东西。

这不是哪里配错了。这就是 UE 正向开发里最核心、也最反直觉的一条惯例：C++ 基类几乎从不直接拿来用，它存在的意义是被某个蓝图继承，然后引擎在配置里引用那个蓝图子类。本篇用 ActionRPG 这个官方示例，带你把这条链子从配置文件一路追到 C++ 头文件。

一、先追一条真实的配置链

打开 Config/DefaultEngine.ini，有三行是这套架构的活样本：

[/Script/EngineSettings.GameMapsSettings]
GameInstanceClass=/Game/Blueprints/BP_GameInstance.BP_GameInstance_C
GlobalDefaultGameMode=/Game/Blueprints/BP_GameMode.BP_GameMode_C

[/Script/Engine.Engine]
AssetManagerClassName=/Script/ActionRPG.RPGAssetManager

这三行里藏着两种完全不同的路径写法，对比着看意思就清楚了：

配置项引擎实际用的类它是什么对应 C++ 基类
GameInstanceClassBP_GameInstance_C蓝图子类URPGGameInstanceBase
GlobalDefaultGameModeBP_GameMode_C蓝图子类ARPGGameModeBase
AssetManagerClassNameRPGAssetManagerC++ 原生类自己（无蓝图）

GameMode 和 GameInstance 走「C++ 基类 + 蓝图子类」两层结构，引擎引用蓝图那一层。AssetManager 例外，直接用 C++ 类。

为什么 AssetManager 不套一层蓝图？因为它干的是资产扫描、按需异步加载这类纯逻辑活，没有需要设计师在编辑器里调的参数，也没有需要可视化连线的事件。套蓝图纯属浪费。而 GameMode、GameInstance 这类，设计师经常要往上挂数据、接事件流（默认背包配置、游戏结束弹什么 UI），所以留了蓝图子类这层给非程序员去装配。

判断标准　有没有给设计师留装配空间，决定了它要不要被蓝图化。

二、插一段基础：那串路径、BP_ 和 _C 到底是什么

上面这几行配置对老手是常识，但第一次见的人多半一脸懵。这一节专门把它们拆开讲清楚，后面看满屏这种路径就不慌了。

路径的通用格式：包路径.对象名

UE 用一种叫「对象路径」的字符串来引用资产或类。关键是中间那个英文句点，它把整条路径切成两半。

把 /Game/Blueprints/BP_GameMode.BP_GameMode_C 沿句点切开
/Game/Blueprints/BP_GameMode
句点左边 = 包路径
指向一个文件（.uasset）
.
BP_GameMode_C
句点右边 = 对象名
指向文件「内部」的对象

读作：在 /Game/Blueprints/BP_GameMode 这个文件里，找名叫 BP_GameMode_C 的对象

为什么左右两边长得几乎一样？因为 UE 的资产文件一般只装一个「主对象」，且默认跟文件同名。文件叫 BP_GameMode，里面那个蓝图主对象也叫 BP_GameMode，我们要的是它编译出来的类 BP_GameMode_C。所以才出现「文件名.类名」这种看着重复的写法。

两个虚拟根：/Game 和 /Script

路径开头那个 /Game 或 /Script，是 UE 给不同来源的东西安排的虚拟根，跟磁盘真实路径不是一回事。

看路径开头，立刻知道这东西的来源
/Game
↓ 映射
Content/ 文件夹
策划做的资产
/Script
↓ 映射
Source/ C++ 模块
程序写的类
/Engine
↓ 映射
引擎自带内容
官方示例/默认资源

换算关系很直接：/Game/Blueprints/BP_GameMode ←→ Content/Blueprints/BP_GameMode.uasset。

而 /Script 后面跟的是「模块名.类名」：

/Script/ActionRPG.RPGAssetManager
         ↑          ↑
       模块名      C++ 类名（去掉 U/A 前缀）

注意类名不带 U 前缀：头文件里是 URPGAssetManager，路径里写 RPGAssetManager。UE 对象路径不带 U/A 这种 C++ 前缀。

BP_ 前缀：只是个命名约定

BP_ 没有任何语法含义，纯粹是习惯，BP 就是 Blueprint 的缩写。引擎不强制，但所有人都这么写，为的是一眼区分蓝图资产和别的东西。顺手记几个常见前缀：

前缀含义例子
BP_蓝图BP_GameMode
WBP_UMG 控件蓝图WBP_Inventory
SM_静态网格SM_Rock
SK_骨骼网格SK_Player
M_ / MI_材质 / 材质实例M_Floor
T_贴图T_Icon_Potion
DA_数据资产DA_Potion_Health

这跟 C++ 那套 U/A/F/I 前缀是两个体系：C++ 前缀给代码看，资产前缀给编辑器里的人看。

_C 后缀：蓝图资产和它编译出的类，是两个东西

这是最容易被忽略、却最该搞懂的点。一个蓝图资产内部不止一个对象。拿 BP_GameMode 举例，它至少装着两样东西：

一个 .uasset 文件里的两个关键对象
BP_GameMode.uasset（文件 / 包）
BP_GameMode
类型 UBlueprint
📐 图纸：编辑器里连节点的设计稿
只在编辑期有意义
BP_GameMode_C
类型 UClass
🏭 模具：运行时拿来 new 实例的类
配置/代码引用的就是它

_C = Class，引擎给蓝图生成类自动加的后缀

打个比方：BP_GameMode 是图纸，BP_GameMode_C 是按图纸造出来的模具，游戏里每个实例都是这个模具压出来的。引擎运行时要的是模具，所以配置里写带 _C 的。写成不带 _C 的，引擎拿到的是图纸而非模具，实例化会失败。

场景要不要写 _C说明
配置文件 .ini✅ 要带引用「可实例化的类」，如 BP_GameMode_C
C++ 代码里引用类✅ 要带本质是引用那个生成的 UClass
编辑器下拉框选蓝图❌ 不用选 BP_GameMode，引擎背后帮你补 _C

C++ 里这俩对象对应两套加载函数：LoadObject 加载 BP_GameMode 拿到图纸（UBlueprint）；LoadClass（或引用 BP_GameMode_C）拿到模具（UClass）。平时跑游戏要的几乎都是后者。

三、两座方向相反的桥：C++ 和蓝图怎么互调

先看 C++ 基类，Source/ActionRPG/Public/RPGGameModeBase.h 整个就这么点：

UCLASS()
class ACTIONRPG_API ARPGGameModeBase : public AGameModeBase
{
    GENERATED_BODY()
public:
    ARPGGameModeBase();

    virtual void ResetLevel() override;
    virtual bool HasMatchEnded() const override;

    /** 游戏结束时调用，比如玩家死了、时间到了 */
    UFUNCTION(BlueprintCallable, Category=Game)
    virtual void GameOver();

protected:
    // 注意这两个：声明在 C++，实现留给蓝图
    UFUNCTION(BlueprintImplementableEvent, Category=Game, meta=(DisplayName="DoRestart"))
    void K2_DoRestart();

    UFUNCTION(BlueprintImplementableEvent, Category=Game, meta=(DisplayName="OnGameOver"))
    void K2_OnGameOver();

    UPROPERTY(BlueprintReadOnly, Category=Game)
    uint32 bGameOver : 1;
};

C++ 这边只定了骨架：状态位 bGameOver、一个能被外部调用的 GameOver()、两个空壳事件。游戏结束后画面怎么变、重开怎么处理，C++ 一字没写，全留给 BP_GameMode 用节点连。这就引出 C++ 和蓝图之间那两条方向相反的桥。

同一个头文件里，两座桥的方向正好相反
C++ 基类
ARPGGameModeBase
──▶BlueprintImplementableEvent
C++ 声明空壳 · C++ 触发调用
蓝图
写实现：弹结算UI、播音效
C++ 实现
GameOver() 写好逻辑
◀──BlueprintCallable
蓝图把它当节点拖出来调
蓝图
血量归零 → 拉 GameOver 节点
BlueprintImplementableEventBlueprintCallable
谁声明C++C++
谁写实现蓝图（图表里）C++（.cpp 里）
谁来调用C++蓝图
一句话C++ 向蓝图要实现（回调钩子）C++ 给蓝图提供能力

K2_ 前缀是 UE 惯例（K2 = Kismet 2，蓝图系统内部代号），配合 meta=(DisplayName="OnGameOver")，蓝图里看到的节点名是干净的 OnGameOver。

踩过的坑　BlueprintImplementableEvent 的函数不能在 .cpp 里写实现，写了会报重复定义。如果你既想给 C++ 默认实现、又允许蓝图覆盖，要用 BlueprintNativeEvent，实现写在 _Implementation 后缀的函数里。这俩别搞混。

四、RPGTypes.h 为什么把一堆东西堆在一起

翻到 Source/ActionRPG/Public/RPGTypes.h，它有点怪：没有完整的类，塞的全是结构体和一长串 delegate 声明。文件头注释写得很直白：

// This header is for enums and structs used by classes and blueprints accross the game
// Collecting these in a single header helps avoid problems with recursive header includes

意思是：这里集中放全游戏跨类共享的 enum 和 struct，集中放是为了躲开头文件递归 include 的麻烦。

左：没有 RPGTypes 时容易绕成环　|　右：抽出公共底座，依赖变单向
RPGItem.h
⇄
PlayerController.h
❌ 你引我、我引你 → 循环依赖编译报错
RPGItem.h
Controller.h
Character.h
↓ ↓ ↓ 都单向 include
RPGTypes.h
公共底座 · 自己几乎不 include 别人
✅ 依赖单向，无环

UE 这种重度依赖头文件和代码生成（每个 UCLASS/USTRUCT 都生成 .generated.h）的项目，循环依赖问题被放大得很厉害。解法就是把「大家都要、谁也离不开」的基础类型抽出来，单放进一个谁都能安全 include、自己却几乎不 include 别人的头文件。

里面那些 delegate 还藏着本项目一个贯穿始终的约定，每个变化都成对声明 dynamic 和 native 两个版本：

// 动态版：蓝图能绑定，慢一点
DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams(FOnInventoryItemChanged, bool, bAdded, URPGItem*, Item);
// 原生版：纯 C++，快
DECLARE_MULTICAST_DELEGATE_TwoParams(FOnInventoryItemChangedNative, bool, URPGItem*);
同一个事件，两个版本各管一边（第五阶段会反复见到）
…ItemChanged
DYNAMIC · 支持蓝图绑定、可序列化
走反射，慢
同一变化，成对发
…ItemChangedNative
纯 C++ 委托 · 只能 C++ 绑
不走反射，快

新增任何跨类共享的 struct 或 delegate，按项目约定都该往这个文件放，别散落到各个类的头文件里。

五、给 C++ 程序员的心智转变

从纯 C++ 过来，最该调的观念是：C++ 定义「能力」，蓝图装配「数据与调参」。

同一个 GameMode，职责怎么分
C++ 基类
类骨架 · 算法 · 性能敏感循环
和引擎底层打交道
提供 GameOver / bGameOver / 事件钩子
蓝图子类
用哪个网格 · 默认放几瓶药
弹哪个 UI · 公式系数填多少
把行为真正装配出来

基类是引擎，蓝图是仪表盘。一个数值、一个表现都没写死在 C++ 里。

承认蓝图的地位，你才读得动这个项目。ActionRPG 一多半的 gameplay 逻辑都在 Content/ 的蓝图里，你抗拒它，就等于自废一半视力。

六、验收清单

学完这阶段，拿下面几条自测，能答上来就算过了。

  1. 看到 RPG*Base 类，立刻反应过来名字里的 Base 就是在喊「我是基类，别直接用」。它八成有个 BP_* 子类躺在 Content/，引擎用的是子类。验证：内容浏览器搜 BP_，右键蓝图选 Class Settings 看 Parent Class。
  2. 看到一个 UFUNCTION，能凭 specifier 判断调用方向：BlueprintImplementableEvent 是 C++ 声明、蓝图实现、C++ 调；BlueprintCallable 是 C++ 实现、蓝图调。前者实现在蓝图图表，后者在 .cpp。
  3. 被问为什么共享类型堆在 RPGTypes.h，能答出「打断头文件循环依赖，统一存放跨类的 enum、struct 和全部 delegate 声明」。
  4. 看到一串对象路径，能拆出包路径与对象名，认出 /Game（资产）/ /Script（C++）/ /Engine（引擎）三个根，并解释 _C 是蓝图编译出的运行时类。

这几条通了，这套「基类被蓝图继承、引擎引用子类」的架构你就真懂了。它是后面每个阶段的入口套路：先在 Source/ 里找 RPG*Base 当锚点读懂能力，再去 Content/ 找 BP_* 看装配。锚点找对了，后面的 Asset Manager、背包、GAS 才不会读得一头雾水。
